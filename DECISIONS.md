# Decisions

Every point where AI-generated output was corrected, rejected, or overridden, and every
non-obvious trade-off. Newest entries at the bottom. This is a deliverable, not a
scratchpad.

## 2026-09-12

- **`flag_resolved` added to the event context, because `variant: 'control'` was ambiguous.** Found by reading `src/lib/analytics/context.ts` rather than from a failing test — no test covered it, and none would have: `currentVariant` initialises to `'control'` and `onVariantResolved` falls back to that same default after its 2000ms timeout, so a flag that was blocked by an ad blocker, slow, or failed outright produced an event indistinguishable from a real control assignment, silently inflating the control arm and biasing the experiment toward "no effect". Fixed by adding a required `flag_resolved: z.boolean()` to `contextSchema`, set in `buildContext()` from the live resolution state, with the timeout path deliberately leaving `variantResolved` false; events carrying `flag_resolved: false` are to be excluded from experiment analysis rather than counted as control.
- **Analytics work committed to `feat/analytics-wiring` rather than onto `main`.** `main` is the default branch and has a remote tracking branch, so committing directly to it was avoided; nothing has been pushed, and folding the branch into `main` is a one-command fast-forward if the branch is unwanted.
- **`$pageleave` and `$feature_flag_called` declared as accepted PostHog system events rather than suppressed or left undocumented.** `$pageleave` is deliberately enabled through `capture_pageleave` and supplies time-on-page, a diagnostic that matters for a landing experience; `$feature_flag_called` cannot be disabled without losing feature flag functionality, which the experiment depends on. `autocapture` and `capture_pageview` remain off, so the funnel is not buried in click noise and `page_viewed` is not shadowed by `$pageview`. The list makes any other `$` event a defect to investigate rather than an open question for a reviewer.
- **`.strict()` was doing nothing on POST /api/users, and a test caught it rather than a reading.** The handler validated `createUserSchema.safeParse({ email: body.email, name: body.name })` — hand-picking the two fields it wanted before validating them. Because the unknown keys never reached the schema, `.strict()` had nothing to reject, and a request carrying `{"name":"Cy Reed","email":"cy@example.com","isAdmin":true}` returned 201 with the extra key silently discarded. I had read that code several times and seen a strict schema; it was exercising the endpoint with curl that produced the 201 and made the gap obvious. Fixed by validating the whole body against a `createRequestSchema` that extends the user schema with an optional `analytics` key and is itself strict, so the body can legitimately carry the analytics envelope while anything else is a 400. The lesson worth keeping: a schema is only strict at the boundary you actually hand it, and picking fields out of a payload moves that boundary without looking like it does.
- **`--fx-market-down` lightened from `#d6454b` to `#db595f` because the original failed WCAG AA.** Measured 3.99:1 against `surface-raised`, under the 4.5:1 floor for body text, which meant the Sell control and every negative P&L figure would have shipped illegible against the panel they sit on. Lightening 11% toward white with the hue unchanged gives 4.65:1 there and 5.51:1 on canvas. It was found by computing every new pairing before writing the markup rather than after, which is the only reason it never shipped; by eye, on a dark panel, the original looked perfectly fine.
- **Email normalisation lives in the Zod schema, not at any call site.** `emailSchema` trims and lowercases as part of parsing, so `"  ANA@Example.COM  "` becomes `ana@example.com` before it reaches the repository, the uniqueness check, or the browser's copy of the same schema. The alternative — normalising in the route handler — puts the guarantee in whichever call site remembers it, and the day someone adds a second write path that forgets, `Ana@example.com` and `ana@example.com` become two accounts and the 409 on duplicate email can be walked around with a capital letter. A rule enforced by a boundary holds; a rule enforced by discipline holds until the next file.
- **Icons were banned in the first design brief and the ban was lifted three briefs later, at a real cost.** The original instruction was to build the proof section with type hierarchy and spacing alone. The result read as text in rectangles, and the fix arrived in stages: first hand-drawn SVG glyphs at 40px, which were too intricate to survive that size and read as scribble; then simplified glyphs in tinted tiles; then the glyphs abandoned entirely for miniatures of the product's own UI, which is what the cards needed from the start. The detour was not wasted — "an icon is worse than nothing here" was correct, and it is what pointed at the miniatures — but a constraint stated as a prohibition removed a compositional tool without naming what should replace it, and three rebuilds of the same section paid for that. Worth stating what a section should contain, not only what it may not.
