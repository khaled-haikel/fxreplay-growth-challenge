# Decisions

Every point where AI-generated output was corrected, rejected, or overridden, and every
non-obvious trade-off. Newest entries at the bottom. This is a deliverable, not a
scratchpad.

## 2026-09-12

- **`flag_resolved` added to the event context, because `variant: 'control'` was ambiguous.** Found by reading `src/lib/analytics/context.ts` rather than from a failing test — no test covered it, and none would have: `currentVariant` initialises to `'control'` and `onVariantResolved` falls back to that same default after its 2000ms timeout, so a flag that was blocked by an ad blocker, slow, or failed outright produced an event indistinguishable from a real control assignment, silently inflating the control arm and biasing the experiment toward "no effect". Fixed by adding a required `flag_resolved: z.boolean()` to `contextSchema`, set in `buildContext()` from the live resolution state, with the timeout path deliberately leaving `variantResolved` false; events carrying `flag_resolved: false` are to be excluded from experiment analysis rather than counted as control.
- **Analytics work committed to `feat/analytics-wiring` rather than onto `main`.** `main` is the default branch and has a remote tracking branch, so committing directly to it was avoided; nothing has been pushed, and folding the branch into `main` is a one-command fast-forward if the branch is unwanted.
- **`$pageleave` and `$feature_flag_called` declared as accepted PostHog system events rather than suppressed or left undocumented.** `$pageleave` is deliberately enabled through `capture_pageleave` and supplies time-on-page, a diagnostic that matters for a landing experience; `$feature_flag_called` cannot be disabled without losing feature flag functionality, which the experiment depends on. `autocapture` and `capture_pageview` remain off, so the funnel is not buried in click noise and `page_viewed` is not shadowed by `$pageview`. The list makes any other `$` event a defect to investigate rather than an open question for a reviewer.
- **`.strict()` was doing nothing on POST /api/users, and a test caught it rather than a reading.** The handler validated `createUserSchema.safeParse({ email: body.email, name: body.name })` — hand-picking the two fields it wanted before validating them. Because the unknown keys never reached the schema, `.strict()` had nothing to reject, and a request carrying `{"name":"Cy Reed","email":"cy@example.com","isAdmin":true}` returned 201 with the extra key silently discarded. I had read that code several times and seen a strict schema; it was exercising the endpoint with curl that produced the 201 and made the gap obvious. Fixed by validating the whole body against a `createRequestSchema` that extends the user schema with an optional `analytics` key and is itself strict, so the body can legitimately carry the analytics envelope while anything else is a 400. The lesson worth keeping: a schema is only strict at the boundary you actually hand it, and picking fields out of a payload moves that boundary without looking like it does.
- **`--fx-market-down` lightened from `#d6454b` to `#db595f` because the original failed WCAG AA.** Measured 3.99:1 against `surface-raised`, under the 4.5:1 floor for body text, which meant the Sell control and every negative P&L figure would have shipped illegible against the panel they sit on. Lightening 11% toward white with the hue unchanged gives 4.65:1 there and 5.51:1 on canvas. It was found by computing every new pairing before writing the markup rather than after, which is the only reason it never shipped; by eye, on a dark panel, the original looked perfectly fine.
- **Email normalisation lives in the Zod schema, not at any call site.** `emailSchema` trims and lowercases as part of parsing, so `"  ANA@Example.COM  "` becomes `ana@example.com` before it reaches the repository, the uniqueness check, or the browser's copy of the same schema. The alternative — normalising in the route handler — puts the guarantee in whichever call site remembers it, and the day someone adds a second write path that forgets, `Ana@example.com` and `ana@example.com` become two accounts and the 409 on duplicate email can be walked around with a capital letter. A rule enforced by a boundary holds; a rule enforced by discipline holds until the next file.
- **Icons were banned in the first design brief and the ban was lifted three briefs later, at a real cost.** The original instruction was to build the proof section with type hierarchy and spacing alone. The result read as text in rectangles, and the fix arrived in stages: first hand-drawn SVG glyphs at 40px, which were too intricate to survive that size and read as scribble; then simplified glyphs in tinted tiles; then the glyphs abandoned entirely for miniatures of the product's own UI, which is what the cards needed from the start. The detour was not wasted — "an icon is worse than nothing here" was correct, and it is what pointed at the miniatures — but a constraint stated as a prohibition removed a compositional tool without naming what should replace it, and three rebuilds of the same section paid for that. Worth stating what a section should contain, not only what it may not.
- **Ad blockers suppressed 100% of client-side telemetry, and nothing in the application noticed.** Every browser event — `page_viewed`, `replay_started`, `trade_opened`, `trade_closed`, `signup_started`, and PostHog's own `$pageleave` and `$feature_flag_called` — was blocked in transport. The only events ever to reach the project were two `account_created`, emitted server-side from `posthog-node`, which no browser extension can touch. The page rendered correctly, the console was clean, the build passed, and the funnel had a numerator and no denominator. It was found by opening PostHog and noticing the project contained exactly one event type, not by any failure surfacing in the app. The diagnosis was settled by confirming that the public key, the api_host and the whole init path were all verifiably present in the shipped client bundle, and that the server — using the *same* key and host — delivered successfully from Node: the only variable left between the working path and the dead one was the browser.
- **That failure mode is load-bearing for this product, not an edge case.** The audience is retail traders researching prop firm evaluations — a population that runs blockers far above the general average, and reaches finance and trading sites where blocking rates are higher still. Any conversion metric built on client-side events will therefore under-count by a margin that is both large and invisible, and will do so unevenly: the visitors most likely to block are not a random sample of the funnel. Two consequences were already designed in and are now vindicated. Emitting `account_created` from the server (invariant 2) is the reason a conversion was recorded at all. And the funnel's denominator, which is client-side by necessity, is the number to distrust.
- **The production mitigation is a reverse proxy on a first-party domain, not a code change.** Routing PostHog through a path on the application's own origin — `/ingest/*` rewritten to the PostHog host — means requests are no longer to a domain on any blocklist. It costs one rewrite rule and a change of `api_host`, and it is the only measure that recovers the blocked population rather than merely measuring the loss. It is deliberately not implemented here: it needs the deployed domain and belongs with the Vercel configuration, not in a local build. Until it exists, treat client-side counts as a floor.
- **The defect worth fixing was the silence, not the blocking.** An analytics layer that delivers nothing and reports nothing is broken whatever the cause. PostHog's own state is enough to detect it without sending a synthetic event: `posthog.init` always requests feature flags, so `onFeatureFlags` failing to fire within a few seconds means no successful round trip happened. The application already subscribed to that callback and discarded the signal. Surfacing it in development turns a silent, hours-late discovery in a dashboard into a console warning within seconds of page load.
- **Production end-to-end verification passed, including the serverless flush.** A full anonymous journey on the deployed site (land, trade twice, post-trade CTA, sign up) produced the whole funnel under one `distinct_id`, and `account_created` arrived from `posthog-node` with that same id, so the identity loop closes in production and not merely in theory. The timing is the part worth keeping: the Supabase row committed at `03:50:09.983Z` and the event carries `03:50:10.065Z` — **81ms later**. That is invariant 2 demonstrated with a measurement rather than asserted, and it is also the proof that `flushAt: 1` plus `await client.shutdown()` survive a serverless function being killed the instant it returns its 201. Without both, the event would have vanished with no error anywhere, which is precisely the failure mode that made server-side emission worth the complexity. `identify()` was additionally confirmed to key the person on the real Supabase `user.id` (`8a9db777…`), matching the row exactly.
- **`replay_started` is lost on every first page load, and the production export is how it surfaced.** The converting journey contains `page_viewed`, `trade_opened` and `trade_closed` but no `replay_started` — while a later visit, reached by client-side navigation back to `/`, emitted it normally. The cause is React effect ordering: child effects run before parent effects, so `ReplayPanel`'s mount effect calls `play("autoplay")` → `markStarted()` → `track('replay_started')` **before** `AnalyticsProvider`'s effect has called `initAnalytics()`. `track()` has no `initialized` guard — unlike `identifyUser` and `getDistinctId`, which both do — so it calls `posthog.capture()` on an uninitialised client and the event is dropped silently. On a client-side navigation the module is already initialised, which is exactly why it works there and nowhere else. Step 2 of the declared conversion funnel is therefore near-zero for every autoplay visitor, making the funnel read as though visitors skip from landing straight to trading. Not fixed in this pass; recorded here because it was found by reading production data rather than by any test.
- **Two undeclared system events arrived: `$web_vitals` and `$experiment_exposure`.** `acceptedSystemEvents` in the tracking plan declares only `$pageleave` and `$feature_flag_called`, and states that any other system event is a defect to investigate. Both new ones are benign — posthog-js performance capture and the experiment exposure the flag system emits — but the list exists so that an unfamiliar `$` event is a question rather than a shrug, and it worked: they were noticed immediately. They should be added to the accepted list with their reasons, or the capture disabled.
- **Assertions still unread at the close of verification.** `flag_resolved` on `page_viewed`, and `entry_point`, `trades_before_signup` and `time_to_signup_ms` on `account_created`. The event export used for verification carried no properties block, and the PostHog MCP was never registered in any session of this build, so none of the four could be read directly. `flag_resolved` is the one that matters: if it is false, the feature flag is not resolving inside the 2000ms window, every visitor is attributed to control by fallback, and the experiment has one arm rather than two.
- **The pre-init queue is verified in production: `replay_started` now survives the mount-before-init race.** A journey on the deployed site produced the event that had been missing from every first page load. The proof is not the timestamp ordering but a three-way comparison in the raw data: `replay_started` carries `variant: control` with `flag_resolved: false`, `page_viewed` from the same `session_id` carries `variant: interactive_replay` with `flag_resolved: true`, and PostHog's own server-side annotation `$feature/hero-interactive-replay` reads `interactive_replay` on **both**. The queued event therefore kept the context built at its emit moment, before the flag had resolved, rather than being rebuilt at flush time. Had it been backdated, the asymmetry would not exist.
- **That same journey is a live instance of the bug `flag_resolved` was added to expose.** The visitor was genuinely in the treatment arm, and `replay_started` nonetheless recorded `variant: control` because the flag had not resolved when the event was emitted. Without the field, that row would have been counted as a control observation and nothing downstream would have revealed it. With it, the row is explicitly excludable. The field earned its place on its first real encounter with the condition it was written for.
- **Correction to the obvious reading of the timestamps.** `replay_started` is stamped `04:15:49.980` and posthog's `$initialization_time` is `04:15:50.110`, which invites the conclusion that the event's timestamp predates initialisation. It does not mean that: posthog-js stamps `timestamp` when `capture()` runs, and for a queued event that is at flush, so the figure records the flush and the original emit was earlier still. The clock is evidence about flush ordering. `flag_resolved: false` is the only thing that proves the emit happened pre-init, because that value could not have been produced afterwards.
- **Known limitation of the verification run: it was not anonymous.** Both events carry `distinct_id: 8a9db777…` — the Supabase `user.id` from the earlier signup — and `$is_identified: true`, because the browser still held that identity. The run therefore proves the queue fix and nothing more. The anonymous-to-identified merge remains proven only by the 03:49 journey, and is not re-proven here. The queue fix itself is unaffected by identity: the race is about React effect ordering, not about who the visitor is.
- **A quirk worth knowing before anyone charts the funnel by timestamp.** `page_viewed` is emitted through `trackWhenVariantReady`, which waits for the feature flag; `replay_started` does not wait. In the verified journey that put `replay_started` 1.14 seconds *before* `page_viewed`, so the funnel's first two steps arrive in the reverse of the order a visitor experiences them. This is correct behaviour — funnel entry must be attributed to the right arm, and that is worth a delay — but a chart ordered on raw timestamp will look wrong to someone who does not know why.
- **The control arm is a skeleton, not a screenshot of a chart.** The obvious control for an interactive replay is a static image of one, and it would look better. It was rejected because the hypothesis isolates exactly one thing — whether letting a visitor take a trade converts better than describing one — and an image would differ from the treatment in visual density, colour, and the amount of market information on screen as well as in interactivity. A lift could then be attributed to any of those, and the experiment would have measured "a picture versus a widget" rather than the question asked. The skeleton reuses the treatment's own chrome: same `Panel`, same title bar, same reserved `aspect-[16/10]`, same gridlines and axis, with the axis ticks as em dashes rather than invented prices for the same reason the evaluation rules panel uses them. The cost is a less impressive control, paid deliberately to keep the comparison clean.
- **The control is rendered during the flag's resolution window, rather than the treatment.** The flag resolves asynchronously and the hero renders before it, so something must be shown in that gap. Rendering the replay first and swapping away would autoplay it and fire `replay_started` for a visitor who belongs to the control arm — not a flicker, a contaminated experiment. Control is also where an unresolved flag lands anyway via the 2000ms fallback, and since ad blockers suppress flag requests for much of this audience, that path is common rather than exceptional; those visitors now see no swap at all. The cost lands on the treatment arm, which grows by the height of the controls row when the flag resolves. That shift is real and was chosen over putting the same shift on the larger population.
- **The performance deferral was measured and the result thrown away rather than banked.** Gating the replay behind flag resolution defers its mount, which is the deferral the performance work called for. Re-running Lighthouse after it shipped gave 55 against a previous 53 — and the number is unusable, because "canvas" appears zero times in the new report: Lighthouse measured the control arm, so 53 and 55 describe two different pages. Recorded as a failed attempt. The run did establish two things that hold regardless: CLS stayed at 0 across the variant switch, and with no canvas on the page at all TBT was *higher* at 3,110ms, with the two longest tasks (963ms, 671ms) in a first-party application chunk while PostHog contributed 2ms of blocking. The dominant cost is React hydration, not the animation loop — which means the fix that looked most promising would have recovered the least.
